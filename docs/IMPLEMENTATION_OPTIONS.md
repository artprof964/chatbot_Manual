## Recommended implementation direction

Build a **database-neutral, incremental revision pipeline first**, with a local API and the same API deployable in cloud. Use immutable content-addressed blobs and versioned manifests as the portable source of truth for rebuilding retrieval stores. Keep one authority for publishing reviewed revisions; distribute those revisions to serving environments. This is the recommended outline decision and does not select a database.

For the first database compatibility spike, **PostgreSQL + Apache AGE + pgvector + PostgreSQL full-text search is now the provisional lead**: it can consolidate evidence, graph, jobs and search into one database, and its components have open-source licenses. The benefit is conditional on released extension compatibility, graph correctness, query plans and a rehearsed upgrade/restore procedure. The previous Neo4j preference reflected graph-development convenience; the new preference reflects the user's stronger open-source and data-maintenance priorities. Jena/Fuseki is the principal fully open-source RDF alternative; Neo4j Community remains a credible open-source graph alternative. No empirical speed ranking is implied.

Keep the portable package contract narrow rather than implementing six production adapters at once. Evaluate all six using that contract; implement native-model evaluation adapters in stages. Do not silently replace AGE with SQL adjacency tables and call it the same candidate: if needed, document that separately as a fallback implementation variant.

## Local/cloud topology and update protocol

The detailed protocol in `PROJECT_OUTLINE.md` sections 2–5 is normative for this outline; the summary below must be read with its complete-capture, fencing, reader-lease and retirement rules. Start locally, then explicitly stop the old publisher and transfer authority to cloud at cutover. Independent serving pointers consume published revisions; they are not independent publication authorities. Publication generation increases monotonically even when rollback selects an older dataset revision.

Recommended default: **one publishing authority, two possible read-serving locations**. Begin with local preparation and local serving. Once a cloud destination exists, upload published revision packages and let the cloud importer build its own staged indexes. Both locations use the same API and expose revision identity, publication time and freshness. Local and cloud can temporarily serve different complete revisions; they must never present those as synchronized. A request cannot switch serving locations midway without restarting and pinning a common available revision.

Local access has two distinct meanings. A local browser calling the cloud API requires connectivity. An autonomous local reader needs local blobs, graph/search indexes, API and a local inference option (or a retrieval-only mode). This outline supports the latter as a deployment profile, but it has not been implemented. Assume offline read access, not offline collaborative writes. Local and cloud annotation writes, when enabled, go to one authoritative API; disconnected editing/conflict resolution is deferred until explicitly required.

Proposed update process:

1. Scan the read-only source and create an immutable snapshot manifest outside the junction. Detect a file changing while read and retry or reject that snapshot. Per-file checks do not guarantee a coherent multi-file release: require a quiescent export or suitable read-only snapshot, validate complete inventory and reject partial/unreadable captures. Incomplete scans must never imply deletion. Preserve each exact source occurrence even when its blob hash already exists.
2. Reuse extracted results only when content plus parser/chunker/config/model identities match. If a linked image or contextual dependency changes, invalidate dependent results. Unknown versions stay unknown; filesystem timestamps do not establish authority.
3. Build a full logical revision manifest containing exact source paths, blob identities, evidence IDs, schemas and derived-artifact dependencies. Deltas transfer only missing immutable objects; a complete manifest makes deletions explicit by absence from the new revision without destroying historical evidence.
4. Transfer missing blobs and derived artifacts with bounded concurrency, resumable object/chunk checkpoints and integrity verification. Credentials and absolute Windows source paths stay outside the portable payload; portable paths are source-relative. Reject traversal paths and unexpected reparse targets. An object key derived from its content hash is separate from the original Unicode evidence path.
5. At the destination, validate the manifest and all required hashes before staging import. Build graph/text/vector views keyed to the new revision. Confirm every evidence reference resolves and every required index is queryable. Do not publish merely because upload finished.
6. Atomically compare-and-swap the destination's active-revision pointer after readiness checks. Every request pins that pointer once; every store/query enforces that revision and authorization scope. Use idempotency keys and durable job leases so retries cannot publish duplicate work or let an older revision overwrite a newer one.
7. Retain the old revision for active readers and rollback. Garbage collect only unreferenced objects after retention and reader-safety checks. Back up review decisions, catalog and immutable manifests; restore and reproduce citations before considering recovery proven.

This is an application protocol, not a claim that a vendor implements cross-store ACID or disconnected synchronization. The shared neutral artifacts allow a database to be rebuilt after moving host or changing engine. Engine-native snapshots can accelerate migration only after testing exact version/edition compatibility. Never synchronize a running database data directory with a file-copy tool.

PostgreSQL dump/restore is a documented migration/backup route, but the extension-specific restore must be tested. PostgreSQL logical replication does not replicate schema/DDL or sequence state; it must not be assumed to transfer a complete AGE deployment or provide conflict-free bidirectional sync. [SQL dump](https://www.postgresql.org/docs/current/backup-dump.html), [logical replication limits](https://www.postgresql.org/docs/current/logical-replication-restrictions.html).

## What “fast” and “easy maintenance” must measure

No transfer or import timing exists. Measure changed bytes, bytes sent, reused blobs/chunks/embeddings, upload elapsed time, import/index elapsed time, end-to-end publication latency and operator interventions. Use unchanged, one-topic edit, linked-image edit, rename, deletion, branch conflict and parser/model-upgrade cases. A parser/model upgrade can invalidate many derived artifacts even if source bytes do not change.

For a transfer payload of B bytes at effective bandwidth R bits/s, the transfer-only floor is approximately 8B/R seconds; retries, round trips, checksums, staging and indexing add time. The historical 741,945,184-byte inventory is not the compressed/deduplicated transfer payload and does not imply a measured cloud-upload duration. Delta transfer is a design intended to reduce repeated work, not a benchmark result.

Track maintenance as a reproducible operator workflow: one update command/job, visible status/errors, retry without manual database repair, documented rollback, pinned dependencies and a restore rehearsal. For the PostgreSQL candidate, first test a released PostgreSQL/AGE/pgvector combination, combined graph/relational transactions, graph index behavior, German full-text exact identifiers, filtered vector recall and upgrade/restore. AGE's repository lists PostgreSQL 11–18 whereas its FAQ lists through 16; release names/tags need inspection rather than assuming the newest branch is a validated stable build. [AGE FAQ](https://age.apache.org/faq/), [release artifacts](https://github.com/apache/age/releases), [pgvector](https://github.com/pgvector/pgvector).

## Decision gates and unresolved questions

Detailed reinspection now supplies 15 source-derived cases and eight synthetic update/failure cases in [SOURCE_TEST_CASES.md](SOURCE_TEST_CASES.md). These include documented operation prerequisites with unknown error-reaction cells, case-sensitive enums, blank versus invalid values, numeric zero versus SQL NULL, a real three-hop dependency chain, a diagram-backed relation, and actual branch additions versus byte-only differences. The case-to-candidate table there further evaluates all six: the findings reinforce evidence fidelity and typed conditional data as common gates, supporting the provisional PostgreSQL/AGE consolidation spike without establishing an empirical winner. The extractor must pass before engine performance is ranked; larger cyclic stress graphs remain explicitly synthetic.

| Gate | Required evidence before a deployment choice |
| --- | --- |
| Open-source and compatibility | Version/license inventory for exact engine, extensions, container runtime, supporting services and inference model; released build smoke tests; managed-host extension support if used. |
| Evidence correctness | Both change-log branches retained; original path/hash/heading evidence resolvable; duplicates preserved as occurrences; no mixed revision answers; conflicting claims remain visible. |
| Maintenance | Unchanged update is idempotent; modified/deleted/renamed content behaves correctly; crash/retry and rollback work; upgrades and restore replay pass. |
| Local/cloud parity | Same frozen revision yields equivalent evidence/results locally and remotely; disconnected local reader works within its documented mode; freshness is explicit. |
| Performance and total effort | Apply the all-six workload in `DATABASE_COMPARISON.md`; collect measured latency, transfer/publication time, cost and operator work. Unsupported or license-blocked runs are marked untested, never assigned invented scores. |

Still unresolved: cloud provider/region and approved destination, real bandwidth, remote-access identity, required offline inference behavior, update frequency, concurrent users, availability/recovery objectives, budget, deployment operating system/runtime, release combinations, rights/policy for source upload, and authority between overlapping change-log branches. These do not prevent drafting the project or local synthetic pipeline tests; they prevent claiming a production-ready, empirically best stack.

Recommendation status: proceed with the neutral pipeline and project outline, give the PostgreSQL/AGE candidate the first compatibility spike, retain all six evaluation records, and defer database selection until the relevant gates pass. Review can close identified design defects; it cannot establish that all possible implementation errors have been eliminated before implementation/testing exists.
